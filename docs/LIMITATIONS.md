# ⚠️ Known limitations, and what was done about them

[← Back to the main README](../README.md)

Honest limits of the current system. Each row says what was done and what remains.

## ⚠️ Limitations

| Limitation | What was done | What remains |
|---|---|---|
| Corrected CIC-IDS2017 is pre-normalised, so attack realism on it is approximate | Pre-normalisation guard; raw-unit original CIC-IDS2017 used as the cross-check and for the deployed detector | Registered numbers on the normalised set stay as registered |
| Research macro-F1 counts absent classes as 0 (time-ordered test) | Labelled follow-up over present classes: 0.104 → 0.469 | — |
| LightGBM collapsed on one NF-ToN-IoT seed | Class weights capped at 50× the median | — |
| ICS gave about 130 false alarms/day | Alarm budget of ≤ 5/day: now 2.06/day | Fewer attacks found (20 / 58); subtle ones stay under the threshold |
| ICS tuning does not transfer (2026-10-16) | Longer look-back / smoothing tried; the setting picked on synthetic-fault validation lost test precision (0.81 → 0.20), so the deployed one is kept | Without labelled real attacks outside the test set there is no honest way to tune further |
| ICS: labelled attacks do not generalise (2026-10-22) | v3 adds HAI 23.05 (works on both plant versions, which v2 did not); a LightGBM hybrid trained on labelled attacks reached precision 0.94 but only recall 0.11 on new attacks | Each HAI attack targets different sensors; recall stays ~0.14-0.23. SWaT / WADI (request from iTrust) or more labelled attack types would be needed |
| Incident view memory at very large stores (fixed 2026-10-23) | Event memory fixed (19.5 GB → 1.8 GB); above 200,000 incidents the view holds only the most severe ones, streamed from the index (same order and boosts as the full view, tested); the incident count stays exact | Views of such stores list the 200,000 most severe incidents |
| Risk-board benefit (fixed 2026-10-24) | The earlier 'no measured gain' came from a bug: the validation scored an EMPTY board. Also fixed: year-less syslog dated in the wrong year, events now keep the machine that logged them (observer), loopback addresses are never entities, failed logons never link entities. Chosen on the AIT development servers, checked on held-out: same-entity boost (weight 1, cap 1) - entity precision 1.00 kept, recall 0.23 → 0.37 (owner decision: entity truth, AIT attackers are dedicated machines). Each site tunes weight / hops from its own reviews (proposed, a user accepts) | One-link-away boosts would reach recall 0.60 but precision 0.95 (an attacker using a real person's account also lifts that person's own incidents), so they stay a per-site choice. Blind round 2 (AIT-LDS v2): no change - every attacker incident was already high |
| OWASP CRS on access logs (2026-10-23) | 106 paranoia-level-1 rules run on the request line, user agent and referer; held-out AIT web servers: attack steps 5 → 6 of 10, attack lines 65.4 % → 66.8 %, false alarms 0 → 0 (results/extra/crs_evaluation.json) | Access logs carry no other headers, cookies or bodies: those rules, chained rules and the libinjection checks (@detectSQLi / @detectXSS) are skipped. Windows Defender flags CRS files: the folder must be excluded |
| Zeek model: 7 % false alarms on the test captures | Settings grid chosen on validation captures: no setting kept test precision and recall, so the deployed one is kept | 2026-10-29: Zeek installed and the third benign IoT-23 honeypot capture (7-1) converted and added to training (test captures unchanged). It held only 359 connections; test precision 0.9956 -> 0.9931 and false alarms 2.8 % -> 4.5 %, so the deployed model is kept. A much larger benign capture would be needed |
| More memory does not always mean more logs/s (fixed 2026-10-25) | Parallel log analysis + measured calibration; event storage made 4× faster; faster rule matching (below) | Re-measured 2026-10-25: ~140,000 logs/s at 2-6 workers, ~190,000 at 8 workers (two runs agree) |
| Windows log mapping | 48 rules, the remote-session rule, the full Sigma bundle (3,161 rules) and 352 LOLBAS / GTFOBins misuse patterns; all Splunk attack_data held-out half: right tactic 38.5 % → 40.9 % with the new parsers. **Blind round 2, EVTX-to-MITRE-Attack (279 recordings): 55.2 % detected, 42.7 % right tactic, 33.7 % right technique.** 2026-10-25 (built-in Windows logs without Sysmon): .evtx files are read in full (they were cut at 5,000 events), remote services through ADMIN$ shares map to lateral movement - held-out right technique 46.9 % → 51.0 %, right tactic 53.9 % (kept) | Single events cannot show every technique |
| Phishing data leak (legitimate URLs are all homepages) | v4 trains on real popular domains (Tranco ranks 200,001-1,000,000) and reads the hostname only, so the homepage-only legitimate URLs no longer teach a path shortcut | Phishing hosted on a trusted shared host (e.g. a cloud drive link) looks like its host; such URLs are checked against the threat-intel feeds instead |
| Flow detectors do not transfer between networks | Flow stack (owner exception 2026-10-24): CIC-IDS2018 recall 0.37 → 0.85, IoT-DIAD 0.14 → 0.84, false alarms lower everywhere; per-site calibration proposes a threshold keeping alerts at 1 % of the site's flows; Zeek FlowMeter input | **Blind round 2, HIKARI: 13.2 % caught at 14.0 % false alarms (before: 0.8 % / 3.8 %)** - no signal on that network. Stack v3 (2026-10-25, owner exception, HIKARI 70 % in training, not blind): HIKARI check 19.4 % caught at 0.009 % false alarms (precision 0.99). After the blind round (not blind): calibration cuts false alarms to 1.0 % / 1.2 % but catches almost nothing; a model trained on 30 % labelled site flows reaches 99.7 % at 2.0 % false alarms on HIKARI-2022 (8.6 % on HIKARI-2021). New networks need labelled site data (Add dataset / analyst reviews) |
| Evasion: PGD flips 31–49 % of detected attacks | Fixed in part (2026-10-25, owner exception): the deployed flow stack v3 learns 150,000 PGD-perturbed attack rows - attacks flipped by PGD on the CIC-IDS2017 test: 41 % → 28 % (ε 0.1), 62 % → 48 % (ε 0.3); v4 (2026-10-25, owner exception, PGD rows at ε 0.1 and 0.3): 29 % (ε 0.1), **31 %** (ε 0.3); energy-based 'manipulated input' flag kept | About a quarter of attacks can still be pushed past the detector by a white-box attacker |
| Rules and threat knowledge go stale (fixed 2026-10-23) | Update agent: Sigma, ATT&CK (incl. new tactics, notified), OWASP Top 10 and OWASP CRS monthly, threat-intel feeds daily; gated (validation, false-alarm check, tests) with rollback | On by default since 2026-10-25 (owner decision); a user can switch it off in Settings -> Updates |
| Unknown log formats were ignored | Structure detection, indicators, rarity, Sigma keywords, parser suggestions | New parsers need the owner's approval |
| Insider data (CERT) is synthetic | Time and unseen-user splits; plain-English reasons | Expect lower accuracy on real organisations |
| Some tactics (for example collection) need endpoint telemetry | Sysmon installer included | Needs Sysmon or an EDR |
| Blind CIC-IDS2018: 56.1 % of attacks caught, 3.85 % false alarms (final round 2026-10-24; 15 Oct: 44.4 % / 1.89 %) | The DDoS specialist caught the HOIC / LOIC floods missing from the 2017 data | Flow detectors do not fully transfer between networks: retrain on the site's own traffic |
| ICS on another plant | Blind HAI 21.03: alarm almost all the time (both rounds). Per-plant fit (2026-10-24, not blind): about 7 days of the plant's normal data finds 45-46 of 50 attacks at 3.7-6.2 false alarms/day, point precision 0.70-0.74; BATADAL 14 / 14 | Each plant needs its own week of normal data; SWaT / WADI (owner's iTrust request) would give a new blind check |
| Blind logs | Round 1 (Splunk, 2026-10-24): 43.8 % detected / 31.9 % right tactic. **Round 2 (AIT-LDS v2): attack steps 5 / 22 and 5 / 21, attack lines 5.2 % / 7.0 %, false alarms 0.003-0.004 %.** After the blind round (not blind; rules written from russellmitchell only, santos is the check): DNS exfiltration / enumeration / PTR sweeps, service-account su, credential files via sudo, sudo -l, web shells in upload folders and base64 commands; Ansible, SMTP 250-VRFY and IDS error false alarms removed. santos: steps 5 → 14 / 21, attack lines 7.0 % → 34.2 %, normal lines alerted 0.004 % → 0.023 % | santos incident precision 0.50 → 0.13 (46 'high' incidents, 6 of the attacker): checked on santos after the owner released it (2026-10-25): 311 of its ~330 normal-line alerts are DNS queries in exactly the tunnelling tool's format (3x6-.N-.), on days AIT did not label - a label gap, not ordinary DNS; the rule is kept. VPN with valid credentials, password cracking (CPU metrics only) and service creation for exfiltration are not caught |
| Blind phishing | Round 1 (OpenPhish): precision 1.00, recall 0.74; round 2 (CompPhish 2024-25): URL v5 recall 0.712 at 2.0 % false alarms, page model recall 0.44. Fixed in part (2026-10-25, owner exception): page model retrained with CompPhish 70 % - on the 30 % check recall 0.39 → 0.64, false alarms 4.0 % → 1.2 %, precision 0.88 → 0.98 (2021 test recall 0.936 → 0.915) | URLs alone catch about 70 % of current phishing; the page model needs the page (uploads / attachments) |
| File scan accuracy on real malware unknown | 0 false alarms on 1,496 signed system files; hits marked low-confidence | Live malware is never downloaded, so detection is not measured |
| Attack recordings can be quarantined by Windows Defender | Results count lost files; Defender left untouched | — |
| macOS never run on real hardware (Linux tested on a real host 2026-10-24) | Linux: the agent ran on Ubuntu (WSL 2, systemd, Python 3.14) and sent auth.log, the systemd journal and a test log over pinned HTTPS to the Windows receiver: 40 / 40 test lines stored once, nothing twice, the host name kept, the SSH brute force became an incident (results/extra/linux_host_test.json) | macOS still only tested by the unit tests (no Mac available) |
| More than 2 parsing workers do not go faster (fixed 2026-10-25) | Workers parse AND store their share; URL verdicts cached; profiling showed parsing was CPU-bound (OWASP CRS 62 %), so CRS now shares decoded values between rules of one request (identical results on 12,510 requests, 1.64× faster) and the evolve-state file is checked every 2 s. 240,000 lines: 64k → **~140k logs/s at 2 workers, ~190k at 8** | Gains depend on the CPU; very large sites still need a SIEM-side index |
| The search index is larger than the raw store | Lean index (2026-10-24): full text for the last N days only, older events read from the store (same results, tested): 200,000 events over 30 days, 7 days of full text: index 186 → 135 MB (-27 %, 3.4× → 2.4× the store) | Word searches over older events are slower |
| UDP syslog cannot confirm delivery (fixed 2026-10-25) | Acknowledged TCP is now the default SIEM transport (TLS and webhook also guaranteed: queue, retries, dead letter); UDP only when a user picks it | UDP itself stays best effort, as in every syslog client |
| The compliance section is evidence, not certification | Every control shows its facts and what to do for gaps | An auditor still decides |
| Agents and the receiver use a self-signed certificate (fixed 2026-10-23) | The receiver can now use the organisation's own certificate (collector.cert_file / key_file); Python agents verify it with ca_file, the Windows agent with the Windows store; the self-signed + pinned mode stays the default | - |
| Rules could not be changed by users (fixed 2026-10-24) | Customise: switch any of 3,612 built-in rules, override severity / technique, exceptions, engine settings, rule packs, proposals from reviews, looser thresholds with a warning - all audited and undoable | Overrides apply to new logs (stored events keep what they had) |
| Popular sites shown as 'suspicious' (fixed 2026-10-25) | The Tranco top 10,000 registered domains (released round-1 blind pool) never get the 'suspicious' warning; a phishing verdict still stands (phishing on big platforms must be caught) | Your own trusted domains: Customise → Allow-list |
